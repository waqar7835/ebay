# eBay Order Management — CLAUDE.md

Multi-tenant order/revenue-share management platform for eBay-style reselling operations. Solo project, pre-launch (no real users yet). Monorepo: pnpm workspaces + Turborepo, one PostgreSQL database shared by three apps.

```
apps/
  backend/     NestJS + Sequelize (sequelize-typescript) — REST API, JWT auth, billing engine, Swagger at /docs
  backoffice/  Next.js 14 (App Router) — Admin/Staff panel (localhost:3001)
  frontend/    Next.js 14 (App Router) — Partner portal for company users (localhost:3000)
packages/
  shared/      TS-types-only package (enums/DTOs). No runtime logic, no shared UI, no shared API client.
```

Full setup/run instructions are in `README.md` — treat the README's setup steps as reliable, but **treat its prose descriptions of features as possibly stale**; verify against code before trusting a claim about what exists. (Known stale spots as of 2026-09-18: it describes a backoffice `/register` flow that doesn't exist yet — see Known Limitations below — and undersells the upload story by saying to "swap for S3-compatible storage before real deployment," when Cloudflare R2 support is already implemented in `apps/backend/src/uploads/uploads.util.ts`.)

The original build plan (`.claude/plans/...`) that the README references **no longer exists in Claude's plan storage** — this file plus memory is now the authoritative source of "why," since that plan can't be recovered.

## Domain model & business rules

- **Companies** self-register (name/email/password/logo), verify email via a 30-minute token or 6-digit code, then log in. `Company.billingAnchorDay` sets their billing cycle start; `Company.staleOrderDays` (default 3) flags orders that have sat too long in an open status — see Known Limitations, it's currently unconfigurable.
- **Roles**: `SUPER_ADMIN`, `PLATFORM_STAFF` (platform-wide, backoffice-only — see Auth Realm Split below), `ADMIN` (company registrant, exactly one per company), `STAFF` (per-company, permission-gated via `staff_profiles`), `ACCOUNT_HOLDER`, `STOCK_OWNER`, `THREE_PL`. A person can hold multiple roles, and — since the multi-account change (commit `18509bf`) — **the same email can have a separate account+password per role**, not one shared login across roles.
- **Products**: `stockOwnerCost` / `buyPrice` / `sellPrice`, plus a fulfillment type: `STOCK` (tied to one 3PL warehouse) or `DROPSHIP` (no 3PL).
- **Orders** (multi-product since 2026-09-28): an order holds one or more **`OrderItem`** rows (`order_items` table: product, Stock Owner, qty, and per-item snapshots of sell/buy/stock-owner cost + Stock Owner share terms). Several items are allowed **only for STOCK products, and all must be held at the same 3PL** (rejected otherwise); a **DROPSHIP order has exactly one item**. Items can belong to different Stock Owners — each Stock Owner is paid per item and their invoice/dashboard counts only their own items (`FinanceService.compute(order, stockOwnerId)`). The **3PL fee is per order, charged once** (`threePlPriceChargedSnapshot`/`threePlPayoutSnapshot` stay on `Order`), as do the Account Holder share snapshot, eBay proceeds and shipping cost. `Order` has a default scope that always loads `items` (ordered by `position`). All revenue-share inputs are **snapshotted at creation** (`*Snapshot` fields) so later rate changes never rewrite history. **Deliberate exceptions (decided 2026-09-28):** editing an order's items (`OrdersService.changeItems`) keeps the snapshot of products that stay on it (only qty changes), snapshots newly added products from current rates, and moves stock by the per-product difference; the 3PL fee is re-snapshotted only when the order's 3PL changes. Changing the *Account Holder* (`changeAccountHolder`) re-snapshots their share % and `threePlPriceCharged`. Both are allowed at any status — **but not once the order is on any invoice** (decided 2026-09-30: `assertNotInvoiced()` in `OrdersService` blocks `update` and the 3PL dropship buy price; status changes stay allowed). To change an invoiced order, delete/void the invoice, edit, re-invoice. See `apps/backend/src/finance/finance.service.ts` — it's a pure function over an order's snapshot, never re-reads live rates.
- **Currencies (decided 2026-09-30)**: every Account Holder / Stock Owner / 3PL user has a `users.currency` (GBP/USD/AUD/EUR/CAD — `Currency` enum in shared; Admin/Staff don't get one). New users are preselected with the company's `companies.default_currency` (GBP for existing companies; set by the company Admin only on the portal Profile page via `POST /companies/me/default-currency`; not on /register; changing it only affects new invites, existing users keep theirs). Each party's amounts are entered in *their* currency: 3PL `payoutPerOrder` + a DROPSHIP 3PL's per-order buy price → 3PL's; AH `threePlPriceCharged`, the order's eBay proceeds + shipping → AH's; product cost/buy/sell → the product's Stock Owner's. Orders convert everything to **PKR** with rates locked on the order (`orders.exchange_rates` JSONB, PKR per unit, + `exchange_rates_at`): the plain / `*Snapshot` amount columns hold **PKR**, the new `*Original` columns + `accountHolderCurrency`/`threePlCurrency`/`order_items.currency` hold what was entered. So `FinanceService` and dashboards are unchanged and all PKR; the UI shows orders/dashboards in PKR only, entry screens in the owner's currency. Invoices: Stock Owner / 3PL invoices are PKR, **Account Holder invoices are in the AH's own currency** (see Invoices). Conversion helpers: `orders/order-currency.util.ts`. Rates: `exchange-rates/exchange-rates.service.ts` pulls `open.er-api.com` (free, no key) at most hourly into the `exchange_rates` table; if the API is down it uses a saved rate < 7 days old (UI warns "API down, saved rate"), otherwise the admin must type the rate in on the order form. The admin can always override any rate on the order form. **Edit**: rates stay locked unless "Recalculate with today's rates" is ticked (`recalculateRates`); a currency new to the order (e.g. new AH in AUD) takes today's/typed rate. Changing a user's currency affects new orders only. **Pre-currency orders** (`exchange_rates` null) are plain PKR (rate 1) until re-saved with Recalculate ticked, which reads their stored amounts as each party's *current* currency and converts them.
- **Revenue share** (exact formulas in `finance.service.ts`, all in PKR):
  - Stock Owner (per item, summed over their items): gross = `buyPrice × qty`; if `PROFIT_SHARE` mode, the company cuts `sharePercent% × (buyPrice − stockOwnerCost) × qty` off that gross; if `FIXED` mode, no cut.
  - Account Holder: profit = `ebayNetProceeds − shippingCost − Σ(sellPrice × qty over items) − threePlPriceCharged`; payout = `profit × sharePercent%`; the remainder stays with the company.
  - 3PL: flat `payoutPerOrder` once per order (not per item), snapshotted at order creation; company markup = `threePlPriceCharged − threePlPayout`.
  - Staff (optional): `sharePercent% × total company profit` (all four sources summed — see `companyProfit()`).
  - All money math rounds to 2 decimals via a local `round2()` helper (duplicated in `finance.service.ts`, `invoices.service.ts`, `dashboard.service.ts`, `billing.service.ts` — not centralized).
- **Users (2026-09-30)**: `DELETE /users/:id` hard-deletes only accounts with no history — anyone on an order (AH / 3PL / item Stock Owner), product or invoice is refused ("disable instead"), since `invoices.user_id` cascades. The company Admin can't be deleted or disabled. Portal users have a profile picture (`users.avatar_url`): set by the user (`POST /users/me/avatar`) or by Admin/Staff with `canManageUsers` (`POST /users/:id/avatar`); JPEG/PNG/WebP only. User pickers and user columns show "Name (Role)" (`userLabel()` in each app's `lib/selectOptions.ts`); search still matches the email.
- **eBay order numbers** (`ebayOrderRef`) are unique per company (trimmed; DB unique index on `(company_id, ebay_order_ref)` + a friendly 409 pre-check in `OrdersService`), enforced on both create and edit.
- **Invoices (redesigned 2026-09-30, replaces the old per-billing-cycle self-service invoices)**: **only the company Admin and Staff with `canGenerateInvoices` create/delete/mark-paid** (portal realm only — `assertPortal()`; the backoffice invoices page is read-only list + PDF download). Everyone else only lists/downloads their own (`GET /invoices`, `GET /invoices/:id/pdf`); Staff with `canViewFinancials` see the whole company's. Wizard at frontend `/invoices/new`: pick user + role (AH / Stock Owner / 3PL only — **Staff revenue-share invoices were dropped**) → tick any open **SHIPPED/DELIVERED** orders (`GET /invoices/invoiceable-orders`) → add any number of misc lines (title + signed amount, in the invoice currency) → Review renders a DRAFT PDF (`POST /invoices/preview`, nothing saved) → Approve (`POST /invoices`). **Per-order invoiced status per role is the invoice id itself** (null = open): `orders.account_holder_invoice_id`, `orders.three_pl_invoice_id`, and `order_items.stock_owner_invoice_id` (**per item**, since one order can mix Stock Owners); claiming uses conditional `UPDATE … WHERE invoice_id IS NULL` + count check so two invoices can't take the same order. **Refunds**: an invoiced order later REFUNDED is offered in the wizard as an optional negative "refund adjustment" line (`*_refund_invoice_id` columns). **Delete** (`DELETE /invoices/:id`): UNPAID → hard delete, PAID → `VOID` (kept for the record); both clear the ids so the orders are open again; blocked while another invoice holds a refund adjustment for one of its orders. Invoice numbers are company initials + year + a per-company counter that never reuses numbers (`companies.last_invoice_sequence`): Alpha Drop → `AD-2026-007`. Lines (`kind` ORDER/REFUND/MISC) snapshot their breakdown in `invoice_line_items.details` JSONB, so the PDF (`invoices/invoice-pdf.ts`, pdfkit, company logo top-left) always re-renders as approved. **Direction/currency**: Stock Owner & 3PL totals are what the company pays them, in PKR (SO layout from the company's sample: cost + (100−company%) of profit). **Account Holder total is what the AH pays the company** — they hold the eBay money: company profit share (100 − AH share %) + buying price (product sellPrice × qty) + 3PL charge + **shipping label reimbursement** (decided 2026-09-30: an order with **no shipping cost** means the label was bought on eBay and is already out of the eBay payout — nothing to add; a **shipping cost entered** on the order means the label was bought outside eBay by the company, so the AH reimburses it — its own column + "Shipping Label Reimbursement" row, shown only when non-zero; Selling = eBay proceeds, profit = selling − buying − 3PL − shipping, i.e. the same profit as `FinanceService`), in the **AH's own currency** (order's locked rate, or today's for orders without one); the AH PDF groups by product, splitting each order's selling/3PL amounts across its products by buying value. **Pre-currency orders can't be invoiced** until re-saved with "Recalculate with today's rates" (their amounts are ambiguous). The dashboards still use `billing-cycle.util.ts` for their default date range.
- **Subscriptions (decided 2026-09-30, replaces per-seat billing)**: every company is on exactly one plan — its paid plan while `companies.subscription_ends_at` (inclusive date) hasn't passed, otherwise the single `is_free` plan (`subscription_plans`; `companies.subscription_plan_id` null = free). A plan caps non-disabled (ACTIVE **or INVITED**) accounts per role: Account Holder / Stock Owner / 3PL / **Staff** (Staff now counts; the company Admin never does). Checked on invite and on re-enable (`SubscriptionsService.assertSeatsAvailable`); lowering a plan's limits never disables anyone. Plans and **billing durations** (`subscription_billing_periods`: months + discount %, default 1/3/6/12 months at 0/5/10/20%) are configured by the Super Admin in backoffice `/subscriptions`; price = monthly price × months − discount. Portal `/subscription`: pick a duration, then a plan, upload a receipt → `subscription_payments` (plan/price/discount snapshotted), one pending at a time; only `SUPER_ADMIN` approves (PLATFORM_STAFF view only). Approval: renewing the same plan before it ends extends from the current end date; a different plan starts today (remaining time is not carried over). The Super Admin can also put a company on a plan directly ("Change plan", no payment). Cron (`subscriptions.scheduler.ts`, midnight + 9am) emails the Admin 5 days and 1 day before expiry (`subscription_reminders_sent`), and on expiry drops the company to the free plan and **disables every account except the Admin** (`users.disabled_by_subscription = true`); the Admin re-enables up to the free plan's limits, and approving a renewal restores flagged accounts oldest-first as far as the new plan allows. Disabled users can't be put on new orders (`isUserDisabled` in `OrdersService`) or accept old invite links. `users.invite_accepted_at` makes re-enabling a never-activated account return it to INVITED rather than ACTIVE.

## Auth realm split — read before touching auth/roles/permissions

**This is the single most load-bearing architectural fact in the codebase.** Two fully separate identity tables, not one shared `users` table with role checks:

- **`backoffice_users`**: `SUPER_ADMIN` / `PLATFORM_STAFF` only. No `companyId` — platform-wide. `PLATFORM_STAFF` is invite-only, created by `SUPER_ADMIN`, with permission flags in `backoffice_staff_profiles`. Logs in only via the backoffice app, sending `context: "backoffice"` on login.
- **`users`** (portal): `ADMIN` / `STAFF` / `ACCOUNT_HOLDER` / `STOCK_OWNER` / `THREE_PL`. `ADMIN` self-registers via frontend `/register`. `STAFF` is invited per-company by that company's own `ADMIN`, permission-gated to their own company (`staff_profiles`). Logs in only via the frontend app (no `context` sent — defaults to portal).
- **Same email can independently exist in both tables** with separate passwords — unrelated identities, not linked. This extends to *within* the portal table too: one email can hold a separate account per role.
- **The JWT `realm: "backoffice" | "portal"` claim is what every guard branches on** — not the `roles` array. See `apps/backend/src/common/company-scope.util.ts` (`resolveCompanyId`) and `apps/backend/src/common/guards/permissions.guard.ts`. Backoffice-realm requests must pass `?companyId=` to act on a company; portal-realm requests are always auto-pinned to their own company from the JWT.
- **Client-side enforcement is by hardcoded call shape, not shared middleware**: backoffice's `login()` always sends `context: "backoffice"`; frontend's never does. Both apps' `lib/api.ts` independently implement `withSelectedCompany()` to append `?companyId=` only when the logged-in user is `SUPER_ADMIN`/`PLATFORM_STAFF` with a company selected via the Nav dropdown.
- Backoffice keeps every original screen (Products/Orders/Users/Invoices/Billing) for Super Admin/Platform Staff cross-company oversight, permission-gated the same way company `STAFF` always was. Frontend has its own near-verbatim copies (minus company-selector logic) for company self-service.

## Conventions

- `packages/shared` is types/enums/DTOs **only** — no shared runtime logic, no shared API client, no shared UI components. `apps/frontend/lib/api.ts` and `apps/backoffice/lib/api.ts` independently reimplement the same `request()`/`authHeaders()`/`getToken()`/`withSelectedCompany()` pattern, and `Nav.tsx`/`AntdProvider.tsx`/`ImageUpload.tsx`/`FileUpload.tsx`/`DateField.tsx` + `lib/selectOptions.ts` exist independently in both apps. **This duplication is intentional** — the two apps are kept decoupled on purpose. Don't "fix" it by introducing cross-app coupling unless asked.
- **UI is antd v6** (both apps; decided 2026-09-28): use antd components instead of raw HTML controls — `Form`/`Input`/`InputNumber`/`Select`/`Table`/`Button`/`Alert`/`Card`/`Tag` etc. Tailwind stays for layout/spacing only. Every `Select` over dynamic data (users, products, companies) must be searchable: `showSearch={searchable}` with options from `userOptions()`/`productOptions()` in `lib/selectOptions.ts`. Product images in lists/forms render through `components/ProductThumb.tsx` (bordered, contain-fit, click to preview the gallery; max `PRODUCT_MAX_IMAGES` = 4 per product). Portal form pages start with `components/BackLink.tsx` (title left, "Back to …" button right). The frontend order create/edit pages share `components/OrderForm.tsx` (two-column card layout like `ProductForm.tsx`). Images go through `components/ImageUpload.tsx` (antd picture-card + `antd-img-crop` crop/rotate/zoom, resized to ≤800px JPEG); non-image files (receipts, PDF labels) through `FileUpload.tsx`; dates through `DateField.tsx` (YYYY-MM-DD strings). Tailwind preflight is wrapped in a lower-priority `@layer tailwind-base` in `globals.css` and `AntdRegistry layer` puts antd in `@layer antd` — keep that ordering or preflight will strip antd button backgrounds. Antd v6 API: `Alert title=` (not `message`), `InputNumber prefix/suffix` (not `addonBefore/After`), `showSearch={{ optionFilterProp }}`.
- **Themes are per role** (decided 2026-09-28), all in the same light multicolor-gradient style: three decorative colors plus one solid functional `colorPrimary` (buttons, links, focus). **Frontend** picks the palette from the logged-in user's role: Admin (and logged-out pages) = "Aurora" (mint `#34d399` / sky `#60a5fa` / lavender `#a78bfa`, primary `#3b82f6`), Staff = "Ocean" (primary `#2563eb`), Account Holder = "Ember" (red/orange/amber, primary `#dc2626`), Stock Owner = "Orchid" (`#9333ea`), 3PL = "Lagoon" (`#0891b2`); an account holding several roles gets the first match in that order. Flat antd tokens + role→theme map live in `apps/frontend/lib/roleTheme.ts` (applied by `AntdProvider.tsx`, re-read on every navigation); gradients live in `app/globals.css` as CSS variables, with Aurora on `:root` and overrides under `html[data-role-theme="<id>"]`; an inline boot script in `layout.tsx` sets that attribute before first paint. **Backoffice** is always "Twilight" (indigo `#818cf8` / lavender `#a78bfa` / lilac `#f0abfc`, primary `#6366f1`), hardcoded in its `AntdProvider.tsx` + `globals.css`. Gradient classes in both apps: `.app-sider`, `.app-logo`, gradient primary buttons, `.kpi-hero` / `.kpi-mint` / `.kpi-sky` / `.kpi-lavender` Statistic cards (the last three are just color slots a/b/c, named after Aurora), `.nav-icon`. Extra colors are decorative only; order-status colors, nav-icon tints and chart colors stay fixed across themes. Font: Plus Jakarta Sans via `next/font` (`--font-jakarta`) in each `layout.tsx`.
- Both Next.js apps have **no `middleware.ts` and no centralized route guard** — every protected page independently does a client-side `useEffect` redirect-if-no-token check. See Known Limitations — this one *is* wanted as a real fix, just not done yet.
- Order financial fields are always snapshotted at creation (`*Snapshot` suffix) — never join back to live `Product`/`*Profile` rates to compute historical financials.
- File uploads (company logo, product images, payment receipts, shipping labels) go through `apps/backend/src/uploads/uploads.util.ts`, which transparently switches between local disk (`UPLOADS_DIR`) and Cloudflare R2 based on whether `R2_ACCOUNT_ID` is set.

## Known limitations / TODOs

Confirmed by reading the code, prioritized per your direction (2026-09-18):

1. **No centralized auth route guard in either Next.js app** (real TODO) — every page duplicates its own `useEffect` redirect check; no `middleware.ts`. Worth building a shared pattern (even if not shared code, given the decoupling convention above — maybe a shared *hook* per app).
2. **`Company.staleOrderDays` has no update endpoint or UI** (real TODO) — read everywhere (dashboard aging-order flags, order-list staleness) but permanently stuck at the DB default of `3`. `billingAnchorDay` has a working `/companies/me/billing-anchor-day` endpoint + UI; `staleOrderDays` needs the equivalent.
3. **Backoffice `/register` flow doesn't exist** (real TODO) — README describes Super Admin registering a company on a client's behalf from backoffice; no such page or API call exists in `apps/backoffice`. Only `POST /auth/register` (used by frontend's self-service `/register`) exists backend-side; backoffice would need its own page calling the same endpoint.
4. **Backoffice has no post-invite edit UI for Account Holder / Stock Owner / 3PL terms** (not yet prioritized) — the portal's `/users/[id]/edit` page edits all three via `PATCH :id/account-holder-profile`, `:id/stock-owner-profile` and `:id/three-pl-profile`; the backoffice `lib/api.ts` doesn't call these endpoints.
5. **No automated tests** — accepted trade-off for now, not a priority while solo/pre-launch.
6. **`PaginatedResult<T>`** (in `packages/shared`) is unused dead code — intentionally left in place as a placeholder for future pagination work, not worth removing.
7. Invoice PDFs are English-only (the AH sample's Urdu labels need RTL shaping pdfkit doesn't do) and omit the "STEP UP TOGETHER" slogan (it's company-specific; would need a company setting). AH company share is rounded per order, so totals can differ by a penny from a sample rounded on the grand total.
8. Backoffice and frontend use different UX patterns for the same create/edit operations (backoffice: inline toggle-forms on list pages; frontend: dedicated routes like `/orders/new`) — functional but inconsistent; not flagged as a priority, just noted so it isn't mistaken for a bug.
