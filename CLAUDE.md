# eBay Order Management — CLAUDE.md

Multi-tenant order/revenue-share management platform for eBay-style reselling operations. Solo project, pre-launch (no real users yet). Monorepo: pnpm workspaces + Turborepo, one PostgreSQL database shared by three apps.

```
apps/
  backend/     NestJS + Sequelize (sequelize-typescript) — REST API, JWT auth, billing engine, Swagger at /docs
  backoffice/  Next.js 14 (App Router) — Admin/Staff panel (localhost:3001)
  frontend/    Next.js 14 (App Router) — public marketing site + Partner portal for company users (localhost:3000)
packages/
  shared/      TS-types-only package (enums/DTOs). No runtime logic, no shared UI, no shared API client.
```

Full setup/run instructions are in `README.md` — treat the README's setup steps as reliable, but **treat its prose descriptions of features as possibly stale**; verify against code before trusting a claim about what exists. (Known stale spots as of 2026-09-18: it describes a backoffice `/register` flow that doesn't exist yet — see Known Limitations below — and undersells the upload story by saying to "swap for S3-compatible storage before real deployment," when Cloudflare R2 support is already implemented in `apps/backend/src/uploads/uploads.util.ts`.)

## Domain model & business rules

- **Companies** self-register (name/email/password/logo), verify email via a 30-minute token or 6-digit code, then log in. `Company.billingAnchorDay` sets their billing cycle start; `Company.staleOrderDays` (default 3) flags orders that have sat too long in an open status — see Known Limitations, it's currently unconfigurable.
- **Roles**: `SUPER_ADMIN`, `PLATFORM_STAFF` (platform-wide, backoffice-only — see Auth Realm Split below), `ADMIN` (company registrant, exactly one per company), `STAFF` (per-company, permission-gated via `staff_profiles`), `ACCOUNT_HOLDER`, `STOCK_OWNER`, `THREE_PL`. A person can hold multiple roles, and — since the multi-account change (commit `18509bf`) — **the same email can have a separate account+password per role**, not one shared login across roles.
- **Products**: `stockOwnerCost` / `buyPrice` / `sellPrice`, plus a fulfillment type: `STOCK` (tied to one 3PL warehouse) or `DROPSHIP` (no Stock Owner, prices, stock or 3PL — those are set per order). A DROPSHIP product needs SKU, title and **at least one image** (decided 2026-10-07; enforced in the product forms and `ProductsService.setImages`); size is optional. Both types are created/edited on the Products page and listed there with a Stock/Dropship tag. **Variations (decided 2026-10-13)**: a product can have color / size variations, each **its own product row** (own SKU — auto-suggested as main SKU-COLOR-SIZE, editable — images, and for STOCK its own cost/buy/sell prices and stock) linked by `products.parent_product_id` (+ `color`, `position`); the main product is the first variation. Title, type, Stock Owner and 3PL always come from the main product (`ProductsService.syncVariations` / `syncVariationsToMain`), so orders, stock, finance and invoices treat a variation as any other product and the order form picks the exact variation. `POST/PATCH /products` take `variations: [...]` (the whole list: with id = update, without = create, left out = delete — refused while it's on an order; omitted = keep them); PATCH on a variation itself is refused. Once a product has variations, it and each variation need a color or a size, and no two may share both. Edited in the portal form's "Variations" card and the backoffice inline form (`components/ProductVariations.tsx`, one copy per app). Paged lists return main products only, each with `variations` (expandable child rows, "Variations" count = main + added; a SKU search also matches variation SKUs); the whole-list response (pickers, dashboards) lists every variation as a product. Labels show color / size: "Title (Red / M)" in pickers / charts, on the SKU line of order lists; invoice lines say "Title — Red / M" for products in a family (`products/product-label.util.ts`). **Stock Owners (2026-10-08)** get a read-only Products page (sidebar Products + Orders links): their own products only, with Cost / Sell price (= buy price) in their currency remaining stock (red "Out of stock" at 0, orange ≤ 5) and **Sold** (units on their own order lines, excluding CANCELLED/REFUNDED orders; `unitsSold` on the `GET /products` response for Stock Owner accounts only). The API enforces it: for a portal Stock Owner account that isn't also Admin/Staff/Account Holder, `GET /products` and `GET /products/:id` return only their own products with `sellPrice` nulled.
- **Orders** (multi-product since 2026-09-28): an order holds one or more **`OrderItem`** rows (`order_items` table: product, Stock Owner, qty, and per-item snapshots of sell/buy/stock-owner cost + Stock Owner share terms). An order is **all-STOCK or all-DROPSHIP** (decided 2026-10-07; the order form has a Stock / Dropshipping switch, and the type **can't change once created**: the switch is locked on edit and `changeItems` rejects it). STOCK: several items, **all held at the same 3PL**. DROPSHIP: **any number of dropship products**, one **optional** 3PL for the whole order (only 3PLs whose profile type is DROPSHIP; a dropship order with no 3PL can't be invoiced or shipped), and each line has two optional prices (decided 2026-10-08), both labelled fields on the admin order form (frontend + backoffice): the **buy price** (`order_items.buy_total_original/_snapshot`: what the 3PL paid for the line, all units together, e.g. 3 pens → 6, in the **3PL's currency**, so it needs a 3PL; the per-unit `buy_price_*` stay null on dropship items) and the **client buying price** (`order_items.client_total_original/_snapshot`: what the company charges the Account Holder for the line, all units, in the **Account Holder's currency** — the dropship counterpart of a STOCK product's sell price). Visibility: Admin/Staff/Super Admin see both; the dropship 3PL only the buy price; the Account Holder only the client price, labelled "Buying price" (`OrdersService.visibleItems` nulls the other one in every order response). Either can be filled in at any time until the order is invoiced, but: **nobody (Admin included) can mark a dropship order SHIPPED/DELIVERED until every line has a buy price** (`assertCanShip`), and the **Account Holder invoice waits for every client price** (the dropship 3PL invoice for every buy price). The assigned 3PL can also enter/correct the buy prices through the Edit popup on its orders list (`components/ThreePlOrderModal.tsx` → `PATCH /orders/:id/three-pl` `{ buyTotals?, supplierUrl? }`, PROCESSING orders only; locked once invoiced). The older `PATCH /orders/:id/dropship-buy-price` `{ itemId, buyTotal }` still exists but the UI no longer calls it. **Dropship 3PL discount (decided 2026-10-27)**: each DROPSHIP 3PL has a `three_pl_profiles.dropship_discount_percent` (default 10, set on the portal 3PL invite/edit pages only), **locked on the order** when its 3PL is set (`orders.three_pl_discount_percent`, re-locked only when the 3PL changes; null = 0). The 3PL is paid each line's buy price less that % — the "admin buy price" (`dropshipNetBuy()`, duplicated in `finance.service.ts` and frontend `lib/orderProfit.ts`): it enters 3, it gets 2.70. The admin order form and price popup show both fields (3PL buy price / Admin buy price; typing either fills the other; only the 3PL price is stored); the admin orders list's Buy Price shows both; the 3PL's list shows its price + "You get …"; its Fulfillment invoice's Dropship section shows Buy price / Discount / Paid (line gross / deduction / net; `details.buyTotal` + `discountPercent`). An empty **client buying price is pre-filled with the 3PL's full price** (not discounted), converted into the AH's currency with the order's rates: by the backend when the 3PL saves its buy prices (`applyDropshipBuyTotals`, only when still empty), and on the admin form/popup while it's empty or still auto-filled; Admin/Staff can change it. Migration 48 gave every open (not 3PL-invoiced) dropship order its 3PL's % and recomputed its payout. The 3PL's payout on a dropship order = the sum of the line admin buy prices, null until every line has a buy price; **there is no 3PL service charge to the Account Holder and no 3PL fee on dropship orders** (`threePlPriceCharged` = 0); removing the 3PL (`threePlId: null` on update) clears the buy prices. **Dropship revenue share is finalized (2026-10-08)** — see Revenue share below. Items can belong to different Stock Owners — each Stock Owner is paid per item and their invoice/dashboard counts only their own items (`FinanceService.compute(order, stockOwnerId)`). The **3PL fee is per order, charged once** (`threePlPriceChargedSnapshot`/`threePlPayoutSnapshot` stay on `Order`), as do the Account Holder share snapshot, eBay proceeds and shipping cost. `Order` has a default scope that always loads `items` (ordered by `position`). All revenue-share inputs are **snapshotted at creation** (`*Snapshot` fields) so later product/profile rate changes never rewrite history — **exchange rates are the exception** (refreshed on every admin save until invoiced; see Currencies). **Deliberate exceptions (decided 2026-09-28):** editing an order's items (`OrdersService.changeItems`) keeps the snapshot of products that stay on it (only qty changes), snapshots newly added products from current rates, and moves stock by the per-product difference; the 3PL fee is re-snapshotted only when the order's 3PL changes. Changing the *Account Holder* (`changeAccountHolder`) re-snapshots their share % and `threePlPriceCharged`. Both are allowed at any status — **but not once the order is on any invoice** (decided 2026-09-30: `assertNotInvoiced()` in `OrdersService` blocks `update` and the 3PL dropship buy price; status changes stay allowed). To change an invoiced order, delete/void the invoice, edit, re-invoice. See `apps/backend/src/finance/finance.service.ts` — it's a pure function over an order's snapshot, never re-reads live rates.
- **Currencies (decided 2026-09-30)**: every Account Holder / Stock Owner / 3PL user has a `users.currency` (GBP/USD/AUD/EUR/CAD — `Currency` enum in shared; Admin/Staff don't get one). New users are preselected with the company's `companies.default_currency` (GBP for existing companies; set by the company Admin only on the portal Profile page via `POST /companies/me/default-currency`; not on /register; changing it only affects new invites, existing users keep theirs). Each party's amounts are entered in *their* currency: 3PL `payoutPerOrder` + a DROPSHIP order's per-line buy totals → 3PL's; AH `threePlPriceCharged`, the order's eBay proceeds + shipping → AH's; product cost/buy/sell → the product's Stock Owner's. Orders convert everything to **PKR** with the rates saved on the order (`orders.exchange_rates` JSONB, PKR per unit, + `exchange_rates_at`): the plain / `*Snapshot` amount columns hold **PKR**, the new `*Original` columns + `accountHolderCurrency`/`threePlCurrency`/`order_items.currency` hold what was entered (a dropship line's client price is in the order's `accountHolderCurrency`, not `order_items.currency`). So `FinanceService` and dashboards are unchanged and all PKR; dashboards and the backoffice show PKR only, entry screens in the owner's currency. **Exception (decided 2026-10-08): the portal orders list shows each viewer's currency** — Admin/Staff and the Account Holder see the order's Account Holder currency (eBay payout as entered; Buy Price / 3PL Fee / Profit = PKR ÷ the order's locked AH rate), a 3PL its own (dropship buy totals as entered), a Stock Owner its own (see Portal orders list); orders without locked rates stay in PKR; each row carries its own symbol, nothing is summed across rows. Invoices: Stock Owner / 3PL invoices are PKR, **Account Holder invoices are in the AH's own currency** (see Invoices). Conversion helpers: `orders/order-currency.util.ts`. Rates: `exchange-rates/exchange-rates.service.ts` pulls `open.er-api.com` (free, no key) at most hourly into the `exchange_rates` table; if the API is down it uses a saved rate < 7 days old (UI warns "API down, saved rate"), otherwise the admin must type the rate in on the order form. The admin can always override any rate on the order form. **Rates aren't locked until invoicing (decided 2026-10-08, replaces lock-at-creation + the "Recalculate with today's rates" checkbox, both removed)**: every create/edit by Admin/Staff re-converts the whole order with today's (or typed) rates (`OrdersService.finalizeAmounts`); saving buy prices from the 3PL popup does *not* refresh them. Since an order on any invoice can't be edited, **the first invoice of any type freezes its rates**, and deleting/voiding that invoice unfreezes them. Product prices / share % stay snapshotted per order as before. **Changing a user's currency (decided 2026-10-14, replaces "affects new orders only")**: an order keeps the party's currency it was created with until the manager updates it. After a currency change, the portal user edit page offers a popup (and a banner while any remain) — and the backoffice Users list has a "Change currency" row action (`components/UserCurrencyModal.tsx`) for Account Holders / Stock Owners / 3PLs that changes the currency and offers the same update — listing that user's open orders still in another currency (`GET /users/:id/orders-off-currency`) → `POST /users/:id/recompute-orders-currency` (`OrdersService.recomputeOrdersCurrency`). The **amounts are kept as typed and re-read in the new currency** (5.60 USD → £5.60; it's for fixing a currency that was set wrong), then converted to PKR again. Rates already on the order stay, and only a currency new to the order gets today's rate. Orders on any invoice and pre-currency orders are skipped. **Pre-currency orders** (`exchange_rates` null) are plain PKR (rate 1) until their next save, which reads their stored amounts as each party's *current* currency and converts them.
- **Revenue share** (exact formulas in `finance.service.ts`, all in PKR):
  - Stock Owner (per item, summed over their items): gross = `buyPrice × qty`; if `PROFIT_SHARE` mode, the company cuts `sharePercent% × (buyPrice − stockOwnerCost) × qty` off that gross; if `FIXED` mode, no cut.
  - Account Holder: profit = `ebayNetProceeds − shippingCost − Σ(line sell total) − threePlPriceCharged`, where a line's sell total is `sellPrice × qty` (STOCK) or its client buying price (DROPSHIP; `lineSellTotal()`); payout = `profit × sharePercent%`; the remainder stays with the company.
  - Product markup (company): Σ(line sell total − line buy), line buy = `buyPrice × qty` (STOCK) or the buy price total less the order's 3PL discount % (DROPSHIP, the admin buy price; 2026-10-27). E.g. dropship payout 25, client price 13, buy price 10, AH 50% → AH profit 12 (6/6), markup 3, company profit 9.
  - 3PL: STOCK — flat `payoutPerOrder` once per order (not per item), snapshotted at order creation; company markup = `threePlPriceCharged − threePlPayout`. DROPSHIP — payout = the sum of the line buy prices less the order's 3PL discount %, no service charge, and that payout is **not** counted again as a negative 3PL markup (it's already in product markup; fixed 2026-10-08, it used to be subtracted twice).
  - Staff (optional): `sharePercent% × total company profit` (all four sources summed — see `companyProfit()`).
  - All money math rounds to 2 decimals via a local `round2()` helper (duplicated in `finance.service.ts`, `invoices.service.ts`, `dashboard.service.ts`, `billing.service.ts`, `orders.service.ts` — not centralized).
- **Users (2026-09-30)**: `DELETE /users/:id` hard-deletes only accounts with no history — anyone on an order (AH / 3PL / item Stock Owner), product or invoice is refused ("disable instead"), since `invoices.user_id` cascades. The company Admin can't be deleted or disabled. Portal users have a profile picture (`users.avatar_url`): set by the user (`POST /users/me/avatar`) or by Admin/Staff with `canManageUsers` (`POST /users/:id/avatar`); JPEG/PNG/WebP only. User pickers and user columns show "Name (Role)" (`userLabel()` in each app's `lib/selectOptions.ts`); search still matches the email — except the portal orders list's Account Holder / 3PL filters the product form's Stock Owner / 3PL pickers and the order form's Client (Account Holder) / 3PL pickers (both apps), which show the name only (`userNameOptions()`, 2026-10-08).
- **3PL auto-delivery (decided 2026-10-08)**: 3PL profiles have "Enable auto-delivery" (off by default) + delivery days (`three_pl_profiles.auto_delivery_enabled/delivery_days/auto_delivery_enabled_at`), on the portal invite/edit pages and the backoffice invite form. Orders the 3PL marks shipped **after it was switched on** (`orders.shipped_at`, set whenever an order enters SHIPPED) move to DELIVERED once that many days pass — hourly cron `orders/orders.scheduler.ts` → `OrdersService.autoDeliver`; STOCK orders wait until they have a tracking number, dropship orders don't. Changing the days keeps the switch-on time; switching off and on again resets it.

For the company Admin and Staff with `canManageOrders`, the list shows clickable status count cards (Total + each status; they use every filter except Status, which is applied client-side), Edit then Status as the first columns, status as a read-only tag, and row checkboxes with a sticky bottom bar to set one status on many orders. The bar opens a confirm popup (order #, current → new status) before `PATCH /orders/status` `{ orderIds, status }`, which runs **all-or-nothing** in one transaction, skips orders already in that status and restocks on CANCELLED like the single-order route; REFUNDED is refused here (one order at a time — see Refunds). **Price popup (2026-10-14)**: for the same users (`canBulkEdit`), double-clicking a Tracking # / Payout / Buy Price / 3PL Fee / Profit cell opens `components/OrderPriceModal.tsx`: tracking number (2026-10-16; blank clears it), eBay payout + shipping and, on dropship orders, each line's buy / client price are editable; stock product prices are shown greyed out (snapshotted); live profit estimate (`components/ProfitRow.tsx`, shared with the order form). Saves through `PATCH /orders/:id` (re-converts at today's rates like any admin save; that route now returns the order with `companyProfit`) and swaps the row in place. Invoiced and pre-currency orders open read-only. **3PL list (reworked 2026-10-08)**: no Status column, no status filter, no Source column; count cards Total / Processing / Shipped / Delivered / Refunded (display-only for a STOCK 3PL, clickable for a DROPSHIP 3PL; Total = the sum of those four) (+ "No tracking #" — SHIPPED/DELIVERED without a tracking number — for STOCK 3PLs only; the dashboard's uninvoiced 3PL cards follow the same rule). A **STOCK 3PL** gets **Processing / Shipped tabs**: Processing rows show units left in stock per product, Print label and a "Mark as shipped" button (row button, or tick rows → bottom-bar "Mark as shipped"; both open the confirm popup); the Shipped tab lists tracking numbers with an edit button (`PATCH /orders/:id/three-pl` `{ trackingNumber }`, PROCESSING/SHIPPED only). The backend rule is unchanged: a 3PL may only move its own orders PROCESSING → SHIPPED, checked per order in the same transaction. - **Invoices (redesigned 2026-09-30, replaces the old per-billing-cycle self-service invoices)**: **only the company Admin and Staff with `canGenerateInvoices` create/delete/mark-paid** (portal realm only — `assertPortal()`; the backoffice invoices page is read-only list + PDF download). Everyone else only lists/downloads their own (`GET /invoices`, `GET /invoices/:id/pdf`); Staff with `canViewFinancials` see the whole company's. Wizard at frontend `/invoices/new`: pick user + role (AH / Stock Owner / 3PL only — **Staff revenue-share invoices were dropped**) → tick any open **SHIPPED/DELIVERED** orders (`GET /invoices/invoiceable-orders`) → add any number of misc lines (title + signed amount, in the invoice currency) → Review renders a DRAFT PDF (`POST /invoices/preview`, nothing saved) → Approve (`POST /invoices`). **Per-order invoiced status per role is the invoice id itself** (null = open): `orders.account_holder_invoice_id`, `orders.three_pl_invoice_id`, and `order_items.stock_owner_invoice_id` (**per item**, since one order can mix Stock Owners); claiming uses conditional `UPDATE … WHERE invoice_id IS NULL` + count check so two invoices can't take the same order. **Refunds (reworked 2026-10-12, replaces the 2026-10-08 rules)**: marking an order REFUNDED is **one order at a time** (the bulk route refuses REFUNDED; the bulk bar offers it only with one order selected) and asks **Full or Partial** (partial = an amount in the AH's currency ≤ the payout, `PATCH /orders/:id/status` `{ status, refundAmount?, restock? }` → `orders.refund_amount(_original)`). A **full STOCK** refund also asks "Is the product coming back?" — yes puts the stock back (`restock: true`); partial refunds never restock; dropship orders are always full, with no restock question. Moving an order out of CANCELLED / REFUNDED after it was restocked takes the units off stock again and clears `orders.restocked`, so a later cancel/refund can restock it (2026-10-12; before, restocking was one-way). **Only an order that was shipped (`shipped_at` set) before the refund is ever invoiced**; one refunded before shipping is never invoiced to anyone. Settlement (`refund-settlement.util.ts`, all per role — each person follows their own invoice id): **STOCK, partial refund R** is used up in this order, in PKR from the order's snapshots, each step split across lines by that line's amount: (1) the company's product markup Σ(sell − buy), (2) the company's PROFIT_SHARE cut, (3) the Stock Owner's profit share (buy − cut − cost) — steps 1–3 show to the AH as "Stock Owner returns"; (4) the AH + company profit (payout − shipping − Σ sell − 3PL charge, floored at 0) split by share %; (5) the product cost (the Stock Owner loses it); (6) anything left is carried by the AH alone. Stock Owner returns = its part of steps 3 + 5; AH credit = steps 1–3 + 5 + the company's part of step 4. E.g. payout 25, sell 10, buy 8, cost 6, SO 50% profit share, 3PL charge 3, AH 50%: refund 5 → markup 2, cut 1, SO profit 1, then AH/company 0.5/0.5 → SO returns 1, AH credit 4.5 (it carries 0.5); refund 20 → 4 (steps 1–3) + 12 (6/6) + 4 of the cost → SO returns 1 + 4 = 5, AH credit 4 + 6 + 4 = 14 (it carries its own 6). **STOCK, full refund**: the Stock Owner returns everything it was paid; the AH gets back the company share + the buying price, i.e. carries only the 3PL charge + shipping (+ loses its own share). **STOCK 3PL** is always paid its fee for a shipped order and never charged back. **Already invoiced** → an optional negative "refund adjustment" line on a later invoice (`*_refund_invoice_id` columns). **Not invoiced yet** → the order is offered with its normal line plus the refund line on the same invoice (both ids claimed together): the AH pays the 3PL charge + shipping on a full refund, a reduced amount on a partial; a Stock Owner's items on a full refund are never offered (it gets nothing; the stock comes back only if ticked), on a partial it's paid its line minus its return. **DROPSHIP**: not invoiced yet → never invoiced (AH or 3PL); invoiced → the 3PL pays back what it was paid (the buy price less its discount) and the company credits the AH everything it paid except shipping (company share + client prices), full or partial alike. Staff have nothing to return. Leaving REFUNDED clears the amount, and is refused once a refund line is on an invoice. **Edit** (`PATCH /invoices/:id`, frontend `/invoices/[id]/edit`, same wizard as create — `components/InvoiceWizard.tsx`): **UNPAID only**, same user + role; the invoice's own orders count as open while editing (`editingInvoiceId` threaded through `candidates()`), and saving releases its old claims and claims the new selection in one transaction, keeping the invoice number and date. **Delete** (`DELETE /invoices/:id`): UNPAID → hard delete, PAID → `VOID` (kept for the record); both clear the ids so the orders are open again; blocked while another invoice holds a refund adjustment for one of its orders. Invoice numbers are company initials + year + a per-company counter that never reuses numbers (`companies.last_invoice_sequence`): Alpha Drop → `AD-2026-007`. ## Auth realm split — read before touching auth/roles/permissions

**This is the single most load-bearing architectural fact in the codebase.** Two fully separate identity tables, not one shared `users` table with role checks:

- **`backoffice_users`**: `SUPER_ADMIN` / `PLATFORM_STAFF` only. No `companyId` — platform-wide. `PLATFORM_STAFF` is invite-only, created by `SUPER_ADMIN`, with permission flags in `backoffice_staff_profiles`. Logs in only via the backoffice app, sending `context: "backoffice"` on login.
- **`users`** (portal): `ADMIN` / `STAFF` / `ACCOUNT_HOLDER` / `STOCK_OWNER` / `THREE_PL`. `ADMIN` self-registers via frontend `/register`. `STAFF` is invited per-company by that company's own `ADMIN`, permission-gated to their own company (`staff_profiles`). Logs in only via the frontend app (no `context` sent — defaults to portal).
- **Same email can independently exist in both tables** with separate passwords — unrelated identities, not linked. This extends to *within* the portal table too: one email can hold a separate account per role.
- **The JWT `realm: "backoffice" | "portal"` claim is what every guard branches on** — not the `roles` array. See `apps/backend/src/common/company-scope.util.ts` (`resolveCompanyId`) and `apps/backend/src/common/guards/permissions.guard.ts`. Backoffice-realm requests must pass `?companyId=` to act on a company; portal-realm requests are always auto-pinned to their own company from the JWT.
- **Client-side enforcement is by hardcoded call shape, not shared middleware**: backoffice's `login()` always sends `context: "backoffice"`; frontend's never does. Both apps' `lib/api.ts` independently implement `withSelectedCompany()` to append `?companyId=` only when the logged-in user is `SUPER_ADMIN`/`PLATFORM_STAFF` with a company selected via the Nav dropdown.
- Backoffice keeps every original screen (Products/Orders/Users/Invoices/Billing) for Super Admin/Platform Staff cross-company oversight, permission-gated the same way company `STAFF` always was. Frontend has its own near-verbatim copies (minus company-selector logic) for company self-service.

Full memory note: `[[auth-realm-split]]`.

Don't "fix" it by introducing cross-app coupling unless asked.
