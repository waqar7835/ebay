# eBay Order Management — CLAUDE.md

Multi-tenant order/revenue-share management platform for eBay-style reselling operations. Solo project, pre-launch (no real users yet). Monorepo: pnpm workspaces + Turborepo, one PostgreSQL database shared by three apps.

```
apps/
  backend/     NestJS + Sequelize (sequelize-typescript) — REST API, JWT auth, billing engine, Swagger at /docs
  backoffice/  Next.js 14 (App Router) — Admin/Staff panel (localhost:3001)
  frontend/    Next.js 14 (App Router) — public marketing site + Partner portal for company users (localhost:3000)
packages/
  shared/      TS-types-only package (enums/DTOs). No runtime logic, no shared UI, no shared API client.
```

Full setup/run instructions are in `README.md` — treat the README's setup steps as reliable, but **treat its prose descriptions of features as possibly stale**; verify against code before trusting a claim about what exists. (Known stale spots as of 2026-09-18: it describes a backoffice `/register` flow that doesn't exist yet — see Known Limitations below — and undersells the upload story by saying to "swap for S3-compatible storage before real deployment," when Cloudflare R2 support is already implemented in `apps/backend/src/uploads/uploads.util.ts`.)

## Domain model & business rules

- **Companies** self-register (name/email/password/logo), verify email via a 30-minute token or 6-digit code, then log in. `Company.billingAnchorDay` sets their billing cycle start; `Company.staleOrderDays` (default 3) flags orders that have sat too long in an open status — see Known Limitations, it's currently unconfigurable.
- **Roles**: `SUPER_ADMIN`, `PLATFORM_STAFF` (platform-wide, backoffice-only — see Auth Realm Split below), `ADMIN` (company registrant, exactly one per company), `STAFF` (per-company, permission-gated via `staff_profiles`), `ACCOUNT_HOLDER`, `STOCK_OWNER`, `THREE_PL`. A person can hold multiple roles, and — since the multi-account change (commit `18509bf`) — **the same email can have a separate account+password per role**, not one shared login across roles.
- **Products**: `stockOwnerCost` / `buyPrice` / `sellPrice`, plus a fulfillment type: `STOCK` (tied to one 3PL warehouse) or `DROPSHIP` (no Stock Owner, prices, stock or 3PL — those are set per order). A DROPSHIP product needs SKU, title and **at least one image** (decided 2026-10-07; enforced in the product forms and `ProductsService.setImages`); size is optional. Both types are created/edited on the Products page and listed there with a Stock/Dropship tag. **Stock Owners (2026-10-08)** get a read-only Products page (sidebar Products + Orders links): their own products only, with Cost / Sell price (= buy price) in their currency and remaining stock (red "Out of stock" at 0, orange ≤ 5). The API enforces it: for a portal Stock Owner account that isn't also Admin/Staff/Account Holder, `GET /products` and `GET /products/:id` return only their own products with `sellPrice` nulled.
- **Orders** (multi-product since 2026-09-28): an order holds one or more **`OrderItem`** rows (`order_items` table: product, Stock Owner, qty, and per-item snapshots of sell/buy/stock-owner cost + Stock Owner share terms). An order is **all-STOCK or all-DROPSHIP** (decided 2026-10-07; the order form has a Stock / Dropshipping switch, and the type **can't change once created**: the switch is locked on edit and `changeItems` rejects it). STOCK: several items, **all held at the same 3PL**. DROPSHIP: **any number of dropship products**, one **optional** 3PL for the whole order (only 3PLs whose profile type is DROPSHIP), and each line has an optional **buy total** (`order_items.buy_total_original/_snapshot`: what the 3PL paid for the line, all units together, e.g. 3 pens → 6, in the **3PL's currency**, so it needs a 3PL; the per-unit `buy_price_*` stay null on dropship items). The admin may enter it on the order form or leave it, and the assigned 3PL can enter or correct it per line once the order is past PENDING, until it's invoiced — **since 2026-10-08 through an Edit popup on the orders list** (DROPSHIP 3PLs only; `components/ThreePlOrderModal.tsx` → `PATCH /orders/:id/three-pl` `{ buyTotals?, supplierUrl?, trackingNumber?, markShipped? }`, one transaction, only while the order is PROCESSING or SHIPPED): line buy totals (locked once invoiced), the supplier URL, the tracking number (optional — they typically mark shipped first and add tracking later) and PROCESSING → SHIPPED; the row shows the order read-only and the inline buy-price inputs are gone. The older `PATCH /orders/:id/dropship-buy-price` `{ itemId, buyTotal }` still exists but the UI no longer calls it. The 3PL's payout on a dropship order = the sum of the line totals, null until every line has one (so it isn't invoiceable to the 3PL before then); removing the 3PL (`threePlId: null` on update) clears the totals. **The rest of the dropship revenue-share formula is deliberately still unfinalized** (AH profit doesn't subtract the dropship buy price; see `FinanceService`), kept for later per the user. Items can belong to different Stock Owners — each Stock Owner is paid per item and their invoice/dashboard counts only their own items (`FinanceService.compute(order, stockOwnerId)`). The **3PL fee is per order, charged once** (`threePlPriceChargedSnapshot`/`threePlPayoutSnapshot` stay on `Order`), as do the Account Holder share snapshot, eBay proceeds and shipping cost. `Order` has a default scope that always loads `items` (ordered by `position`). All revenue-share inputs are **snapshotted at creation** (`*Snapshot` fields) so later rate changes never rewrite history. **Deliberate exceptions (decided 2026-09-28):** editing an order's items (`OrdersService.changeItems`) keeps the snapshot of products that stay on it (only qty changes), snapshots newly added products from current rates, and moves stock by the per-product difference; the 3PL fee is re-snapshotted only when the order's 3PL changes. Changing the *Account Holder* (`changeAccountHolder`) re-snapshots their share % and `threePlPriceCharged`. Both are allowed at any status — **but not once the order is on any invoice** (decided 2026-09-30: `assertNotInvoiced()` in `OrdersService` blocks `update` and the 3PL dropship buy price; status changes stay allowed). To change an invoiced order, delete/void the invoice, edit, re-invoice. See `apps/backend/src/finance/finance.service.ts` — it's a pure function over an order's snapshot, never re-reads live rates.
- **Currencies (decided 2026-09-30)**: every Account Holder / Stock Owner / 3PL user has a `users.currency` (GBP/USD/AUD/EUR/CAD — `Currency` enum in shared; Admin/Staff don't get one). New users are preselected with the company's `companies.default_currency` (GBP for existing companies; set by the company Admin only on the portal Profile page via `POST /companies/me/default-currency`; not on /register; changing it only affects new invites, existing users keep theirs). Each party's amounts are entered in *their* currency: 3PL `payoutPerOrder` + a DROPSHIP order's per-line buy totals → 3PL's; AH `threePlPriceCharged`, the order's eBay proceeds + shipping → AH's; product cost/buy/sell → the product's Stock Owner's. Orders convert everything to **PKR** with rates locked on the order (`orders.exchange_rates` JSONB, PKR per unit, + `exchange_rates_at`): the plain / `*Snapshot` amount columns hold **PKR**, the new `*Original` columns + `accountHolderCurrency`/`threePlCurrency`/`order_items.currency` hold what was entered. So `FinanceService` and dashboards are unchanged and all PKR; dashboards and the backoffice show PKR only, entry screens in the owner's currency. **Exception (decided 2026-10-08): the portal orders list shows each viewer's currency** — Admin/Staff and the Account Holder see the order's Account Holder currency (eBay payout as entered; Buy Price / 3PL Fee / Profit = PKR ÷ the order's locked AH rate), a 3PL its own (dropship buy totals as entered), a Stock Owner its own (see Portal orders list); orders without locked rates stay in PKR; each row carries its own symbol, nothing is summed across rows. Invoices: Stock Owner / 3PL invoices are PKR, **Account Holder invoices are in the AH's own currency** (see Invoices). Conversion helpers: `orders/order-currency.util.ts`. Rates: `exchange-rates/exchange-rates.service.ts` pulls `open.er-api.com` (free, no key) at most hourly into the `exchange_rates` table; if the API is down it uses a saved rate < 7 days old (UI warns "API down, saved rate"), otherwise the admin must type the rate in on the order form. The admin can always override any rate on the order form. **Edit**: rates stay locked unless "Recalculate with today's rates" is ticked (`recalculateRates`); a currency new to the order (e.g. new AH in AUD) takes today's/typed rate. Changing a user's currency affects new orders only. **Pre-currency orders** (`exchange_rates` null) are plain PKR (rate 1) until re-saved with Recalculate ticked, which reads their stored amounts as each party's *current* currency and converts them.
- **Revenue share** (exact formulas in `finance.service.ts`, all in PKR):
  - Stock Owner (per item, summed over their items): gross = `buyPrice × qty`; if `PROFIT_SHARE` mode, the company cuts `sharePercent% × (buyPrice − stockOwnerCost) × qty` off that gross; if `FIXED` mode, no cut.
  - Account Holder: profit = `ebayNetProceeds − shippingCost − Σ(sellPrice × qty over items) − threePlPriceCharged`; payout = `profit × sharePercent%`; the remainder stays with the company.
  - 3PL: flat `payoutPerOrder` once per order (not per item), snapshotted at order creation (DROPSHIP orders: the sum of the line buy totals instead); company markup = `threePlPriceCharged − threePlPayout`.
  - Staff (optional): `sharePercent% × total company profit` (all four sources summed — see `companyProfit()`).
  - All money math rounds to 2 decimals via a local `round2()` helper (duplicated in `finance.service.ts`, `invoices.service.ts`, `dashboard.service.ts`, `billing.service.ts`, `orders.service.ts` — not centralized).
- **Users (2026-09-30)**: `DELETE /users/:id` hard-deletes only accounts with no history — anyone on an order (AH / 3PL / item Stock Owner), product or invoice is refused ("disable instead"), since `invoices.user_id` cascades. The company Admin can't be deleted or disabled. Portal users have a profile picture (`users.avatar_url`): set by the user (`POST /users/me/avatar`) or by Admin/Staff with `canManageUsers` (`POST /users/:id/avatar`); JPEG/PNG/WebP only. User pickers and user columns show "Name (Role)" (`userLabel()` in each app's `lib/selectOptions.ts`); search still matches the email.
- **Portal orders list (decided 2026-10-08)**: for the company Admin and Staff with `canManageOrders`, the list shows clickable status count cards (Total + each status; they use every filter except Status, which is applied client-side), Edit then Status as the first columns, status as a read-only tag, and row checkboxes with a sticky bottom bar to set one status on many orders. The bar opens a confirm popup (order #, current → new status) before `PATCH /orders/status` `{ orderIds, status }`, which runs **all-or-nothing** in one transaction, skips orders already in that status and restocks on CANCELLED/REFUNDED like the single-order route. **3PLs get the same list (2026-10-08)**: counts without a PENDING card, no Edit column, Status first (with the stale ⚠ tag), Print label last; only their PROCESSING rows are selectable and the bar only offers SHIPPED (the backend rule is unchanged: a 3PL may only move its own orders PROCESSING → SHIPPED, checked per order in the same transaction). A STOCK-type 3PL doesn't see the Buy Price column; a DROPSHIP 3PL still enters line buy totals there. Account Holder / Stock Owner (and Staff without `canManageOrders`) keep the old inline status dropdown. **Stock Owner view (2026-10-08)**: per product line (lined up with Products, total when 2+ lines) Cost / Sell price (= the buy price the company pays them) / Profit / Your share (= sell − the PROFIT_SHARE cut, i.e. cost + their part of the profit, as on their invoice), **in the Stock Owner's own currency** from the items' `*Original` fields (PKR on pre-currency orders); the eBay Payout column is hidden from them. **Account Holder view (2026-10-08)**: Payout / Buying price (Σ product sellPrice × qty, order total) / 3PL charge / Shipping (— when bought on eBay) / Profit (= payout − buying − 3PL − shipping, as on their invoice) / Your share (profit × share %), all in their currency: payout, 3PL charge and shipping as entered, buying price converted with the order's locked AH rate (PKR on pre-currency orders).
- **Order comments (decided 2026-10-08)**: `orders.comments` (TEXT, ≤ 2000 chars) — Admin/Staff notes for the 3PL, set on the order form's "Comments" card ("" clears on edit). Only managers and 3PLs receive it (`OrdersService` nulls it for Account Holders / Stock Owners on list and `GET /orders/:id`). On the orders list (for every 3PL, Stock or Dropship, and Admin/Staff) the Order # cell shows a red info icon: hover = tooltip clamped to 2 lines, click = popup with the full comment; the dropship 3PL Edit popup shows it read-only at the top.
- **eBay order numbers** (`ebayOrderRef`) are unique per company (trimmed; DB unique index on `(company_id, ebay_order_ref)` + a friendly 409 pre-check in `OrdersService`), enforced on both create and edit.
- **Invoices (redesigned 2026-09-30, replaces the old per-billing-cycle self-service invoices)**: **only the company Admin and Staff with `canGenerateInvoices` create/delete/mark-paid** (portal realm only — `assertPortal()`; the backoffice invoices page is read-only list + PDF download). Everyone else only lists/downloads their own (`GET /invoices`, `GET /invoices/:id/pdf`); Staff with `canViewFinancials` see the whole company's. Wizard at frontend `/invoices/new`: pick user + role (AH / Stock Owner / 3PL only — **Staff revenue-share invoices were dropped**) → tick any open **SHIPPED/DELIVERED** orders (`GET /invoices/invoiceable-orders`) → add any number of misc lines (title + signed amount, in the invoice currency) → Review renders a DRAFT PDF (`POST /invoices/preview`, nothing saved) → Approve (`POST /invoices`). **Per-order invoiced status per role is the invoice id itself** (null = open): `orders.account_holder_invoice_id`, `orders.three_pl_invoice_id`, and `order_items.stock_owner_invoice_id` (**per item**, since one order can mix Stock Owners); claiming uses conditional `UPDATE … WHERE invoice_id IS NULL` + count check so two invoices can't take the same order. **Refunds**: an invoiced order later REFUNDED is offered in the wizard as an optional negative "refund adjustment" line (`*_refund_invoice_id` columns). **Edit** (`PATCH /invoices/:id`, frontend `/invoices/[id]/edit`, same wizard as create — `components/InvoiceWizard.tsx`): **UNPAID only**, same user + role; the invoice's own orders count as open while editing (`editingInvoiceId` threaded through `candidates()`), and saving releases its old claims and claims the new selection in one transaction, keeping the invoice number and date. **Delete** (`DELETE /invoices/:id`): UNPAID → hard delete, PAID → `VOID` (kept for the record); both clear the ids so the orders are open again; blocked while another invoice holds a refund adjustment for one of its orders. Invoice numbers are company initials + year + a per-company counter that never reuses numbers (`companies.last_invoice_sequence`): Alpha Drop → `AD-2026-007`. Lines (`kind` ORDER/REFUND/MISC) snapshot their breakdown in `invoice_line_items.details` JSONB, so the PDF (pdfkit; styled by the invoice's frozen template — see Invoice templates) always re-renders as approved. **Direction/currency**: Stock Owner & 3PL totals are what the company pays them, in PKR (SO layout from the company's sample: cost + (100−company%) of profit). **Account Holder total is what the AH pays the company** — they hold the eBay money: company profit share (100 − AH share %) + buying price (product sellPrice × qty) + 3PL charge + **shipping label reimbursement** (decided 2026-09-30: an order with **no shipping cost** means the label was bought on eBay and is already out of the eBay payout — nothing to add; a **shipping cost entered** on the order means the label was bought outside eBay by the company, so the AH reimburses it — its own column + "Shipping Label Reimbursement" row, shown only when non-zero; Selling = eBay proceeds, profit = selling − buying − 3PL − shipping, i.e. the same profit as `FinanceService`), in the **AH's own currency** (order's locked rate, or today's for orders without one); the AH PDF groups by product, splitting each order's selling/3PL amounts across its products by buying value. **Pre-currency orders can't be invoiced** until re-saved with "Recalculate with today's rates" (their amounts are ambiguous). The dashboards still use `billing-cycle.util.ts` for their default date range. **Every dashboard section (Company / AH / SO / 3PL) shows "Not invoiced yet" count cards** (decided 2026-10-08): Total + one card per status (3PL: no PENDING), all time, ignoring the dashboard filters, from `uninvoiced` on each dashboard response (`DashboardService.uninvoiced`). Per role "invoiced" = that role's invoice id (AH/3PL on the order, SO per item); for the Company view an order counts while any side is still open (AH, 3PL if it has one, or any Stock Owner item). The cards are `components/StatusCounts.tsx`, shared with the orders list (clickable there, display-only on the dashboard).
- **Invoice templates (decided 2026-09-30)**: an invoice PDF's style = one of five **fixed layouts** (`InvoiceLayout`: Classic / Split Header / Sidebar / Soft Cards / Bold — redesigned 2026-09-30 so each has its own layout and color family: slate+gold, ocean blue, emerald, coral on cream, berry+black) + five **colors** (page background, heading background = `accent`, heading text, body text, borders) + a logo. Five **predefined** templates (one per layout, in code: `PREDEFINED_INVOICE_TEMPLATES` in shared, ids `classic`…) plus up to **five custom** per company (`invoice_templates`: name, layout, colors JSONB, optional own `logo_url` — null = company logo; PNG keeps transparency; optional `watermark` JSONB). **Predefined templates are editable per company (decided 2026-10-02)**: the Admin can change their colors, logo and watermark (name/layout stay fixed) and reset them (`POST /invoice-templates/:key/reset`); an edit is an `invoice_templates` row with `predefined_key` set (unique per company + key), which doesn't count toward the custom limit — predefined ones can't be deleted or copied from their row; a new template picks any template under "Start from". **Watermark (decided 2026-10-02)**: per template, optional (`InvoiceWatermark` in shared: enabled, text — prefilled with the company name, color, size 12–150pt, opacity 5–60%, rotation −90..+90° with positive = clockwise, repeat + horizontal/vertical gaps 20–300pt; limits in `INVOICE_WATERMARK_LIMITS`). Drawn on top of every page; when enabled it shows on the wizard's draft preview **and** on issued invoices and replaces DRAFT, while VOID is still drawn over it; when off, DRAFT/VOID behave as before. Only the company **Admin** manages them (portal Profile → "Invoice templates" card → `/profile/invoice-templates/new?from=…` / `[id]/edit`, with a live sample-PDF preview) and sets the company default (`companies.default_invoice_template_id`, null/deleted = Classic); anyone who creates invoices picks any template on the wizard's Review step (preselected: the invoice's own when editing, else the default); the backoffice only lists them (read-only, on its Invoices page). **Each invoice freezes its style at approval** (`invoices.template` JSONB snapshot incl. the resolved logo URL and the watermark) — editing/deleting a template never changes issued PDFs; editing an UNPAID invoice re-snapshots from the picked template. **Invoices with `template` null (issued before templates) still render through the original `invoice-pdf.ts` unchanged**; everything else goes through `invoice-pdf-templated.ts` (content model per role → layout drawing; same figures/wording as the original, but table cells show plain numbers with the currency in the header/note, and **no Status in the header** — DRAFT/VOID (or the template's own watermark) show only over the page; decided 2026-09-30). Details are always drawn as label-over-value cells/lists, never one line that can overflow. Profit stays green and VOID red in every template. **Each invoice type has its own content** (same in every layout): Account Holder "ACCOUNT INVOICE" (product breakdown → what the AH owes), Stock Owner "INVOICE" (item sales & profit → cost + profit share), **3PL "FULFILLMENT INVOICE" (decided 2026-09-30)**: separate **Stock Fulfillment** (fee per order) and **Dropship Purchases** (the buy price the 3PL entered) sections, each row = order #, date, products × qty, tracking #, status, amount, with subtotals; final box = fulfillment fees + dropship reimbursement + adjustments. 3PL lines snapshot `fulfillment`/`status`/`trackingNumber`/`products` in `details` (optional fields — 3PL lines approved before that show under a plain "Orders" section with blanks). Table columns are never narrower than their longest word (order/tracking numbers, statuses and dates never break); a table that can't fit steps its font down slightly.
- **Subscriptions (decided 2026-09-30, replaces per-seat billing)**: every company is on exactly one plan — its paid plan while `companies.subscription_ends_at` (inclusive date) hasn't passed, otherwise the single `is_free` plan (`subscription_plans`; `companies.subscription_plan_id` null = free). A plan caps non-disabled (ACTIVE **or INVITED**) accounts per role: Account Holder / Stock Owner / 3PL / **Staff** (Staff now counts; the company Admin never does). Checked on invite and on re-enable (`SubscriptionsService.assertSeatsAvailable`); lowering a plan's limits never disables anyone. Plans and **billing durations** (`subscription_billing_periods`: months + discount %, default 1/3/6/12 months at 0/5/10/20%) are configured by the Super Admin in backoffice `/subscriptions`; price = monthly price × months − discount. Portal `/subscription`: pick a duration, then a plan, upload a receipt → `subscription_payments` (plan/price/discount snapshotted), one pending at a time; only `SUPER_ADMIN` approves (PLATFORM_STAFF view only). Approval: renewing the same plan before it ends extends from the current end date; a different plan starts today (remaining time is not carried over). The Super Admin can also put a company on a plan directly ("Change plan", no payment). Cron (`subscriptions.scheduler.ts`, midnight + 9am) emails the Admin 5 days and 1 day before expiry (`subscription_reminders_sent`), and on expiry drops the company to the free plan and **disables every account except the Admin** (`users.disabled_by_subscription = true`); the Admin re-enables up to the free plan's limits, and approving a renewal restores flagged accounts oldest-first as far as the new plan allows. Disabled users can't be put on new orders (`isUserDisabled` in `OrdersService`) or accept old invite links. `users.invite_accepted_at` makes re-enabling a never-activated account return it to INVITED rather than ACTIVE.

## Auth realm split — read before touching auth/roles/permissions

**This is the single most load-bearing architectural fact in the codebase.** Two fully separate identity tables, not one shared `users` table with role checks:

- **`backoffice_users`**: `SUPER_ADMIN` / `PLATFORM_STAFF` only. No `companyId` — platform-wide. `PLATFORM_STAFF` is invite-only, created by `SUPER_ADMIN`, with permission flags in `backoffice_staff_profiles`. Logs in only via the backoffice app, sending `context: "backoffice"` on login.
- **`users`** (portal): `ADMIN` / `STAFF` / `ACCOUNT_HOLDER` / `STOCK_OWNER` / `THREE_PL`. `ADMIN` self-registers via frontend `/register`. `STAFF` is invited per-company by that company's own `ADMIN`, permission-gated to their own company (`staff_profiles`). Logs in only via the frontend app (no `context` sent — defaults to portal).
- **Same email can independently exist in both tables** with separate passwords — unrelated identities, not linked. This extends to *within* the portal table too: one email can hold a separate account per role.
- **The JWT `realm: "backoffice" | "portal"` claim is what every guard branches on** — not the `roles` array. See `apps/backend/src/common/company-scope.util.ts` (`resolveCompanyId`) and `apps/backend/src/common/guards/permissions.guard.ts`. Backoffice-realm requests must pass `?companyId=` to act on a company; portal-realm requests are always auto-pinned to their own company from the JWT.
- **Client-side enforcement is by hardcoded call shape, not shared middleware**: backoffice's `login()` always sends `context: "backoffice"`; frontend's never does. Both apps' `lib/api.ts` independently implement `withSelectedCompany()` to append `?companyId=` only when the logged-in user is `SUPER_ADMIN`/`PLATFORM_STAFF` with a company selected via the Nav dropdown.
- Backoffice keeps every original screen (Products/Orders/Users/Invoices/Billing) for Super Admin/Platform Staff cross-company oversight, permission-gated the same way company `STAFF` always was. Frontend has its own near-verbatim copies (minus company-selector logic) for company self-service.

## Conventions

- `packages/shared` is types/enums/DTOs **only** — no shared runtime logic, no shared API client, no shared UI components. `apps/frontend/lib/api.ts` and `apps/backoffice/lib/api.ts` independently reimplement the same `request()`/`authHeaders()`/`getToken()`/`withSelectedCompany()` pattern, and `Nav.tsx`/`AntdProvider.tsx`/`ImageUpload.tsx`/`FileUpload.tsx`/`DateField.tsx` + `lib/selectOptions.ts` exist independently in both apps. **This duplication is intentional** — the two apps are kept decoupled on purpose. Don't "fix" it by introducing cross-app coupling unless asked.
- **UI is antd v6** (both apps; decided 2026-09-28): use antd components instead of raw HTML controls — `Form`/`Input`/`InputNumber`/`Select`/`Table`/`Button`/`Alert`/`Card`/`Tag` etc. Tailwind stays for layout/spacing only. Every `Select` over dynamic data (users, products, companies) must be searchable: `showSearch={searchable}` with options from `userOptions()`/`productOptions()` in `lib/selectOptions.ts`. Product images in lists/forms render through `components/ProductThumb.tsx` (bordered, contain-fit, click to preview the gallery; max `PRODUCT_MAX_IMAGES` = 4 per product). Portal form pages start with `components/BackLink.tsx` (title left, "Back to …" button right). The frontend order create/edit pages share `components/OrderForm.tsx` (two-column card layout like `ProductForm.tsx`). **Dates (decided 2026-10-08)** display as `DD MMMM YYYY` ("08 October 2026"), with a time as `DD MMMM YYYY, HH:mm`, via `formatDate`/`formatDateTime` in each app's `lib/date.ts`; `DateField` shows the same format but still reads/writes YYYY-MM-DD. Invoice PDFs keep their own date format. Images go through `components/ImageUpload.tsx` (antd picture-card + `antd-img-crop` crop/rotate/zoom, resized to ≤800px JPEG); non-image files (receipts, PDF labels) through `FileUpload.tsx`; dates through `DateField.tsx` (YYYY-MM-DD strings). Tailwind preflight is wrapped in a lower-priority `@layer tailwind-base` in `globals.css` and `AntdRegistry layer` puts antd in `@layer antd` — keep that ordering or preflight will strip antd button backgrounds. Antd v6 API: `Alert title=` (not `message`), `InputNumber prefix/suffix` (not `addonBefore/After`), `showSearch={{ optionFilterProp }}`.
